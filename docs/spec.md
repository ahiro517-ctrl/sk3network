# sk3 人脈マップ システム仕様書

バージョン: 1.0
対象範囲: スプレッドシート入力 → Web関係図への自動反映
ステータス: スペック駆動開発のための初版

---

## 1. このシステムは何か

sk3 コミュニティの人・プロジェクト・テーマの関係を可視化する Web 関係図システム。コミュニティメンバー全員が 1 つのスプレッドシートに情報を入力すると、その内容が Web 上の関係図に反映される。

関係図は単なる「人脈図」ではなく「意図の地図」である。テーマ(やってみたいこと、視察に行きたい場所、関心ごと)を主役に置き、人はその周りに「これに乗りたい」という意思表示として配置される。描くのは既存の関係ではなく、これから生まれうる関係の予兆。コミュニティイベントの場で図を見ながら、まだつながっていない人を戦略的につなぐために使う。

### 1.1 スコープ

本仕様書が対象とするのは以下の 2 つのコンポーネントと、その間のデータの流れである。

- 入力: Google スプレッドシート(コミュニティメンバーが共同編集)
- 出力: Web 関係図(ブラウザで閲覧。スプレッドシートの内容を反映)

### 1.2 スコープ外(将来拡張)

- Discord からの入力。現時点では実装しない。将来、入力をより気軽にしたくなった場合に「スプレッドシートへ書き込む別ルート」として追加しうる。
- Obsidian 連携。現時点では実装しない。メンバーが人物ごとに文章メモを書きためる文化が育った場合に追加を検討する。

## 2. 全体アーキテクチャ

データの流れは一方向である。

```
[メンバー全員]
     │  入力
     ▼
[Google スプレッドシート]  ← データの唯一の源(Single Source of Truth)
     │  公開・変換
     ▼
[中間ステップ: データ取得層]
     │  整形済みデータ
     ▼
[Web 関係図(ブラウザ)]  ← 閲覧
```

設計の根幹となる原則は「データの源は 1 つ」である。スプレッドシートだけが真実のデータを持ち、Web 関係図はそれを表示するだけ。Web 側でデータを編集することはない。

### 2.1 「中間ステップ」の 2 案

スプレッドシートの内容を Web 関係図に届ける方法は 2 通りある。スペック駆動開発の最初の意思決定ポイントである。

**案 A: 直接読み込み方式(推奨)**

Web ページが、開かれるたびに Google スプレッドシートの内容を直接取得して描画する。Google スプレッドシートは内容を CSV または JSON として配信する機能を持つため、Web 関係図の HTML/JS がそれを読み込む。

- メリット: 構成がシンプル。サーバー不要。メンバーがシートに書く → 関係図を開く → 反映、という分かりやすい動き。
- 反映タイミング: 「リアルタイム」ではなく「ページを開いた(リロードした)時点で最新」。実用上はこれで十分。
- 注意: スプレッドシートを外部から読める形にするため、その URL を知ると生データにアクセスできる。後述のセキュリティ設計(セクション 6)で対応する。

**案 B: 定期ビルド方式**

一定間隔(例: 1 時間ごと)で、スクリプトがスプレッドシートを読み HTML またはデータファイルを生成し直す。

- メリット: 表示が速い。生データの URL を外部に晒さずに済む。
- デメリット: 最新反映にタイムラグ。定期実行の仕組み(サーバーまたはクラウドの定期実行)が必要。

**本仕様の推奨: 案 A(直接読み込み方式)**。理由は構成がシンプルでサーバー管理が不要なこと、メンバーから見た動きが直感的なこと。セキュリティはデータの分離(セクション 6)で担保する。

## 3. スプレッドシートの構造

Google スプレッドシート 1 ファイルの中に、以下のシートを置く。

| シート名 | 役割 | 編集者 |
|---|---|---|
| 使い方 | 記入ルールの説明 | 事務局が用意、メンバーは読むだけ |
| 人 | 人ノードの情報 | メンバー全員 |
| プロジェクト | プロジェクトノードの情報 | 事務局が主に管理 |
| テーマ | テーマノードの情報 | メンバー全員 |
| 関わり | 人とプロジェクト/テーマの結びつき | メンバー全員 |

設計の方針として、ノードの情報(人・プロジェクト・テーマ)と、ノード同士の結びつき(関わり)を別シートに分ける。これにより 1 人が複数のプロジェクトやテーマに関わる状況を、行を増やすだけで素直に表現できる。

## 4. 各シートの列定義

凡例: 必須列は「必須」、任意列は「任意」と記載。「入力方式」はメンバーがどう値を入れるかを示す。

### 4.1 「人」シート

1 行 = 1 人。

| 列名 | 必須/任意 | 入力方式 | 説明 |
|---|---|---|---|
| ID | 必須 | 自動 or 手動 | 人を一意に識別するキー。重複不可。下記 4.6 参照。 |
| 表示名 | 必須 | 自由入力 | 内部ビューで表示される名前。実名・呼び名など。 |
| 公開名 | 任意 | 自由入力 | 公開ビューで表示される名前。ニックネームやコード。空の場合は自動採番(M01 等)。 |
| 立場 | 必須 | プルダウン | 事務局 / コアメン / フォロワー のいずれか。 |
| sk3所属 | 必須 | プルダウン | あり / なし(外部) のいずれか。 |
| スキル | 任意 | プルダウン(複数可) | デザイン / 編集 / 撮影 / ライティング / エンジニア / 企画 / 広報 / 場づくり 等。 |
| 所属企業 | 任意 | 自由入力 | 内部ビューのみ表示。公開ビューでは非表示または略称化。 |
| 知り合った日 | 任意 | 日付入力 | YYYY-MM 形式。 |
| ひとこと | 任意 | 自由入力 | 自己紹介や近況。「自分が書ける範囲で」記入。 |

注記: 「立場」の二重性に注意。ここでの「立場」はコミュニティ全体での立場(事務局/コアメン/フォロワー)である。「あるプロジェクトのコアメンバーかどうか」は別概念であり、4.4「関わり」シートの「関わり方」列で表現する。混同しないこと。

### 4.2 「プロジェクト」シート

1 行 = 1 プロジェクト。

| 列名 | 必須/任意 | 入力方式 | 説明 |
|---|---|---|---|
| ID | 必須 | 自動 or 手動 | プロジェクトを一意に識別するキー。重複不可。 |
| プロジェクト名 | 必須 | 自由入力 | 表示名。 |
| 公式区分 | 必須 | プルダウン | 公式 / 非公式。 |
| 発信元 | 必須 | プルダウン | sk3発 / 外部発。 |
| オープン | 必須 | プルダウン | オープン / クローズ。オープンは新規参加者を歓迎中。 |
| 関わりしろ | 任意 | 自由入力 | オープンな場合、どんな人を求めているかの説明。 |
| 概要 | 任意 | 自由入力 | プロジェクトの一言説明。 |
| ステータス | 任意 | プルダウン | 構想中 / 進行中 / 完了 / 保留。 |

### 4.3 「テーマ」シート

1 行 = 1 テーマ。テーマとは「やってみたいこと」「視察に行きたい場所」「関心ごと」など、人を引き寄せる呼びかけ。プロジェクトより軽く、寿命が短い。

| 列名 | 必須/任意 | 入力方式 | 説明 |
|---|---|---|---|
| ID | 必須 | 自動 or 手動 | テーマを一意に識別するキー。重複不可。 |
| テーマ名 | 必須 | 自由入力 | 表示名。「〇〇に視察に行きたい」等。 |
| 言い出した人 | 任意 | プルダウン(人ID) | このテーマを最初に挙げた人。 |
| 説明 | 任意 | 自由入力 | テーマの補足。 |
| 状態 | 必須 | プルダウン | 募集中 / 実現した / 終了。下記 4.5 の寿命管理に使う。 |
| 有効期限 | 任意 | 日付入力 | 「次回イベントまで」等の目安。 |

### 4.4 「関わり」シート

1 行 = 1 つの結びつき。人が、どのプロジェクトまたはテーマに、どう関わっているかを表す。1 人が複数に関わる場合は複数行になる。

| 列名 | 必須/任意 | 入力方式 | 説明 |
|---|---|---|---|
| 人ID | 必須 | プルダウン(人ID) | 「人」シートの ID を選ぶ。 |
| 対象種別 | 必須 | プルダウン | プロジェクト / テーマ。 |
| 対象ID | 必須 | プルダウン(対象のID) | 「プロジェクト」または「テーマ」シートの ID を選ぶ。 |
| 関わり方 | 必須 | プルダウン | コア / メンバー / 関心あり。下記参照。 |

「関わり方」の値の意味:

- コア: そのプロジェクト/テーマの中心メンバー。Web 関係図では太い線で表現。
- メンバー: 通常の参加者。
- 関心あり: 「気になる」「乗ってみたい」レベルの弱い接続。フルに参加表明しなくても、点として存在を可視化できる。内向的な人やまだ何者でもない人を拾うための重要な選択肢。

設計意図: 人同士を直接つなぐリンクは作らない(検討の結果、線が増えすぎて俯瞰しにくくなるため不採用)。人と人は、同じプロジェクトやテーマに関わることで間接的につながる。

### 4.5 テーマの寿命管理

テーマには寿命を持たせる。「テーマ」シートの「状態」列で管理し、Web 関係図での見え方を変える。

- 募集中: 通常表示。オープンなテーマとして強調(脈打つ表示など)。
- 実現した: 達成済みとして塗りつぶし表示。一定期間後に非表示にしてよい。
- 終了: 実現せず終わったもの。非表示またはグレーアウト。

人ノードは消さずに残す。テーマが動いて人が残ることで「あのテーマは終わったが、あの人はまだいる」が見え、次の接続のきっかけになる。

### 4.6 ID の扱い

各ノード(人・プロジェクト・テーマ)には一意の ID を持たせる。ID は結びつきを表す「関わり」シートから参照される。

- 表記ゆれ対策として、結びつきは名前文字列ではなく ID で指定する。「関わり」シートの人ID・対象ID 列はプルダウンにして、既存の ID からしか選べないようにする。これにより「能登学会」と「能登 学会」のような不一致を構造的に防ぐ。
- ID の付与方法は実装時に決定する。候補: (a) 行追加時に自動採番、(b) 事務局が手動付与。プルダウン連動を考えると自動採番が望ましい。

## 5. データ検証ルール

スプレッドシート上で、可能なものはプルダウン(データの入力規則)で強制する。プルダウンにすべき列は各表の「入力方式」欄に明記済み。

入力ミスは Web 関係図の表示崩れに直結するため、以下を仕様とする。

- 必須列が空の行は、Web 関係図への変換時に除外し、エラーとして記録する。
- 「関わり」シートで、存在しない人IDや対象IDを参照する行は除外し、エラーとして記録する。
- 同一 ID の重複は検出して警告する。
- これらのエラーは、変換時にレポートとして出力し、事務局が点検・修正できるようにする。

完全な自動修復は目指さない。事務局(仲介役)が時々データを点検する運用は残る前提とする。

## 6. セキュリティ設計(内部ビュー / 公開ビュー)

実名・所属企業・スキル・人間関係が 1 枚に集まると、外部に出してはいけない情報資産になる。これに対し「表現を削る」のではなく「出し分ける」で対応する。

### 6.1 2 つのビュー

- 内部ビュー: コミュニティメンバーが見る。表示名(実名等)・所属企業まで表示。
- 公開ビュー: 外部に見せる場合に使う。公開名(ニックネーム/コード)に置き換え、所属企業は非表示。スキルは粗い粒度に留める。

### 6.2 データ分離の方針

案 A(直接読み込み方式)を採る場合、Web が読むデータの URL を知れば中身が見える。したがって、公開ビュー用には実名・企業名を含まないデータを別に用意し、Web の公開ビューはそちらだけを読む。具体的な分離方法(別シートにするか、公開用の列だけを配信するか)は実装時に決定する。

内部ビューと公開ビューで、参照するデータの実体そのものを分けることを仕様とする。1 つのデータにビューだけかぶせる方式は、生データが漏れるため公開用途では採用しない。

### 6.3 公開範囲

ネットでの一般公開はしない。外部に見せる場合も、リンクを知る人だけがアクセスできる限定公開を基本とする。多くの場合、完全公開ではなく「メンバーとその周辺」で目的を達せる。

注意点として、ニックネーム化しても、プロジェクト構成や人間関係の形そのものから個人が推測されうる。「公開ビューにすれば完全に安全」とは考えない。

### 6.4 「つなぎ提案」は図に載せない

事務局が「この人とこの人を会わせたい」と考えた仮説は、関係図そのものには書き込まない。図は参加者の自己申告だけで構成する。つなぎの仮説は事務局用の別メモ(別レイヤー)に置く。理由: 全員が見る図に他人が勝手に線を引くと、薄くしか描かれていない参加者が不安を感じ、継続率に影響する。図を綺麗に保つことが参加者の安心につながる。

## 7. Web 関係図の表示仕様

### 7.1 ノードの種類と見た目

| ノード | 形 | 色分けの基準 | 大きさの基準 |
|---|---|---|---|
| 人 | 円 | 立場(事務局/コアメン/フォロワー) | 立場、または関わりの数 |
| プロジェクト | 四角 | 公式(実線枠)/非公式(破線枠) | 参加人数 |
| テーマ | 四角(別形状) | 状態(募集中/実現した/終了) | 関心を寄せる人数 |

### 7.2 リンクの種類

- 人 → プロジェクト、人 → テーマの 2 種類のみ。人 → 人は引かない。
- 「関わり方」が「コア」のリンクは太線で強調。
- 「関わり方」が「関心あり」のリンクは細い線または点線で、弱い接続として表現。

### 7.3 インタラクション(既存サンプルで実装済みの想定機能)

- ノードをタップで詳細パネル表示。
- ノードのドラッグで移動、ホイール/ピンチで拡大縮小。
- 立場・プロジェクト種別などでのフィルタ表示。
- 内部ビュー / 公開ビューの切り替え。ただしセクション 6.2 のとおり、公開ビューは公開用データを参照する。
- オープンなプロジェクト/募集中テーマの強調表示(脈打つ表現など)。
- 俯瞰のヒント: sk3 所属だがプロジェクト/テーマ未参加の人を検出して提示するなど、つなぎの発見を補助する表示。

### 7.4 反映タイミング

案 A 採用時、Web 関係図はページを開いた時点のスプレッドシート内容を表示する。メンバーがシートを更新後、関係図をリロードすれば最新になる。常時自動で線が動くリアルタイム同期ではない。

## 8. 運用フロー

### 8.1 通常運用

1. 事務局が「プロジェクト」シートに既知のプロジェクトを事前登録しておく(表記ゆれ防止のため、メンバーが新規入力ではなく選択できる状態にする)。
2. メンバーが「人」「テーマ」「関わり」シートに自分の情報を追記する。「自分が書ける範囲で」記入する旨を案内する。
3. Web 関係図を開くと、最新のスプレッドシート内容が反映されている。
4. 事務局が定期的にデータを点検し、エラーレポート(セクション 5)を見て修正する。

### 8.2 イベントでの使い方

コミュニティイベントの事前、チェックイン時、またはイベント内のワークショップとして、参加者がテーマや関わりを記入し図を育てる。事務局・コアメンが図を見ながら、まだつながっていない人や、テーマとそれに関心を持つ人を結ぶ仮説を立て、声がけする。

## 9. スペック駆動開発のための実装ステップ

以下の順で開発する。各ステップは前のステップの完了を前提とする。

1. **意思決定**: 中間ステップを案 A(直接読み込み)に確定する。セキュリティのためのデータ分離方法(セクション 6.2)を具体化する。
2. **スプレッドシート構築**: セクション 3・4 の定義どおりに Google スプレッドシートを作成。プルダウン(入力規則)を設定。「使い方」シートを記入。
3. **サンプルデータ投入**: 動作確認用に、人・プロジェクト・テーマ・関わりの仮データを入れる。
4. **データ取得層の実装**: スプレッドシートを Web から読める形(CSV/JSON 配信)にし、内部用・公開用のデータを分離する。
5. **Web 関係図の改修**: 既存の Web 関係図サンプルを、固定データではなくスプレッドシート由来のデータを読み込む形に作り替える。テーマノードと「関心あり」リンクに対応させる。
6. **検証ルールの実装**: セクション 5 のエラー検出とレポート出力を組み込む。
7. **公開設定**: Web 関係図を限定公開できる場所(GitHub Pages 等)に配置。
8. **運用開始とイベント投入**: セクション 8 の運用フローで回す。

### 9.1 既存の資産

- Web 関係図サンプル(30 人規模・全機能入りのアップグレード版)が作成済み。立場の色分け、公式/非公式、コア線、パルス、内部/公開ビュー切替、フィルタ、俯瞰ヒントを実装済み。ステップ 5 はこれをベースに改修する。ただし現サンプルは「人脈図」段階で、テーマノードと「関心あり」リンク(意図の地図の中核)は未実装のため、これを追加する。
- 記入用テンプレートと変換スクリプトが作成済み。スプレッドシート設計とデータ変換の参考にする。

## 10. 用語集

| 用語 | 意味 |
|---|---|
| 意図の地図 | このシステムが描くものの本質。既存の関係ではなく、これから生まれうる関係を可視化する。 |
| ノード | 関係図上の点。人・プロジェクト・テーマの 3 種類。 |
| リンク | ノード同士をつなぐ線。本システムでは人とプロジェクト/テーマの間にのみ引く。 |
| テーマ(□) | やってみたいこと・関心ごと。人を引き寄せる呼びかけ。プロジェクトより軽く寿命が短い。 |
| 関わり方 | 人がプロジェクト/テーマにどう関わるか。コア / メンバー / 関心あり。 |
| 内部ビュー | メンバー向け表示。実名・企業名まで見える。 |
| 公開ビュー | 外部向け表示。匿名化され、企業名は出ない。 |
| データの源 | スプレッドシートを指す。システム内で唯一の真実のデータ。 |
| 案 A / 案 B | 中間ステップの 2 方式。A=直接読み込み(推奨)、B=定期ビルド。 |
